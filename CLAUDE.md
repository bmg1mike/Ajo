# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Ajo is a proof of concept for a messaging-first JAMB Biology study companion: small accountability "circles" with cited RAG answers, daily lessons, peer nudges, and weekly payouts. `spec.md` is the source of truth for behavior and acceptance criteria (section 16); `plan.md` orders the work into a foundation phase plus milestones 1–10. The foundation (config, DB models, migrations, virtual clock, privacy helpers, adapter registry), milestone 1 (corpus ingestion), milestone 2 (cited QA), milestone 3 (Telegram onboarding; native-speaker review of the Yoruba/Pidgin UI strings still pending), milestone 4 (daily lessons and grading), milestone 5 (virtual days, personas, batched feed, scheduler), milestone 6 (inactivity detection and peer nudges) and milestone 7 (weekly payout; together milestones 1–7 are the minimum demo), milestone 8 (voice; the native-speaker listening check of Yoruba audio is still pending) and milestone 9 (web simulator, `web/simulator.html`) are done. Note that `AGENTS.md` still describes these directories as unimplemented and is partly stale.

## Commands

```bash
uv sync                                   # install deps (incl. dev group: pytest, httpx)
cp .env.example .env                      # then set HASH_SALT to >= 32 chars (required)
docker compose up -d db                   # Postgres 16 + pgvector on 127.0.0.1:5432
uv run alembic upgrade head               # app refuses to start until migrations have run
uv run fastapi dev                        # dev server; entrypoint is app.main:app (pyproject [tool.fastapi])

uv run pytest                                             # full suite (SQLite only by default)
uv run pytest tests/test_foundation.py::test_clock_advances_accumulate
uv run pytest -k "clock and sqlite"                       # DB tests are parametrized [sqlite] / [postgres]
TEST_DATABASE_URL=postgresql+psycopg://ajo:ajo@localhost:5432/ajo uv run pytest   # also run Postgres variants
uv run alembic revision --autogenerate -m "..."           # new migration in migrations/versions/

uv run python -m ingest.ingest --sources ingest/sources.yaml   # build corpus (downloads ~590 MB PDFs on first run)
uv run python -m ingest.ingest --dry-run --offline            # report only; no downloads, no DB writes
AJO_CORPUS_TESTS=1 uv run pytest -m corpus                     # milestone 1 check on real PDFs + e5 model

uv run python -m app.core.qa_eval                  # milestone 2: 20-question eval vs ingested DB + configured LLM
uv run python -m app.core.qa_eval --retrieval-only # threshold tuning; no LLM calls
AJO_QA_EVAL=1 uv run pytest -m qa_eval             # same check as a test (no live calls once the cache is warm)
uv run python -m app.core.i18n --review yo        # Markdown review sheet of UI strings for a native speaker (yo | pcm)
uv run python -m app.core.lessons --pregenerate    # milestone 4: validated fallback lesson + yo/pcm translations per topic
uv run python -m app.core.opportunities            # which data/opportunities.json entries a payout would show today
uv run python -m app.sim.rehearse --database-url <copy of the DB>   # minimum demo end to end; counts LLM cache misses
uv run python -m app.sim.rehearse --database-url <copy> --voice      # also Listen + a spoken question (needs ffmpeg/libopus)
uv run python -m app.speech.tts --review yo --out review-yo          # lesson audio + sheet for a native-speaker listening check
AJO_SPEECH_TESTS=1 uv run pytest -m speech                           # real MMS-TTS -> ffmpeg -> faster-whisper round trip
```

With `TEST_DATABASE_URL` set, the Postgres fixture creates and drops a throwaway `ajo_test_<uuid>` database, so the configured user needs CREATEDB. Without it, the Postgres variants are skipped. No linter or formatter is configured.

## Architecture

- **App factory**: `app/main.py:create_app(settings, services=..., telegram=...)` builds the app. The lifespan creates the engine, then attaches `settings`, `sessions` (sessionmaker), `clock`, `adapters`, `qa`, `lessons`, `demo` and `conversation` to `app.state`, and checks that the `clock_state` singleton row exists. Background workers are passed as `services`: async context-manager factories taking the app. They are entered in order, then Telegram polling if `TELEGRAM_ENABLED`, and all are torn down before the engine is disposed. The module-level `app` passes `services=[scheduler_service]`, while `create_app()` alone runs no services, so tests opt in. Tests replace the Bot API through the `telegram` factory (`telegram_polling(app, request=FakeRequest(...))`). Root `main.py` only re-exports `app`.
- **Sessions**: `app/db.py:get_session` is the request dependency (one transaction per request). `build_engine` supports SQLite (enables foreign keys) as well as Postgres.
- **Dual-dialect models**: `app/models.py` must work on both Postgres and SQLite, because tests run against both. Use the existing variant types: `JSON_TYPE` (JSONB→JSON), `UUID_LIST` (ARRAY(Uuid)→JSON), and `Vector(384).with_variant(JSON(), "sqlite")`. Enums are non-native string enums with check constraints (`enum_type`). Schema changes need an Alembic migration. `migrations/env.py` accepts an injected connection via `config.attributes["connection"]`, which the tests use, and migrations must stay idempotent because the tests run `upgrade head` twice. A migration that changes how existing rows behave must backfill them; `tests/conftest.py` provides `throwaway_database` and `migrate(engine, revision)` for upgrade tests from an older revision (see `test_upgrading_expires_nudges_queued_before_expiry_existed`).
- **Virtual clock** (`app/core/clock.py`): `now()` = real UTC + `offset_seconds`, stored in the singleton `clock_state` row (seeded by migration 0001). Business logic must use `app.state.clock.now()`, never `datetime.now()`. `advance()` accepts only positive whole seconds and updates atomically in SQL.
- **Adapters** (`app/adapters/base.py`): core code calls `AdapterRegistry.send_*`, which routes by `learner.channel` and silently skips learners for whom `Learner.receives_messages` is false (personas, unless a web pane controls them). Core must never import a concrete adapter. Keep adapters thin.
- **Privacy** (`app/core/privacy.py`): `channel_hash` produces salted SHA-256 hashes (channel user IDs and phone numbers are never stored raw). `delete_learner(..., confirmed=True)` relies on FK `ON DELETE CASCADE`, and it also scans `feed_events`, `outbound_deliveries`, `llm_cache` and `web_messages` JSON for learner identifiers and deletes matching rows. When you add tables that reference learners, give them a cascading FK or extend this scan.
- **Ingestion** (`ingest/`): `sources.yaml` (catalog: PDF URL, pinned SHA-256, license, footer `line_patterns`, and sections named by exact PDF bookmark title) → `pdf.py` (slices each section between its bookmark and the next one, splitting mid-page at the heading line; printed page numbers come from footers, inferred from neighbours on chapter openers) → `chunking.py` (300–500 e5 tokens, 50-token word overlap, never crossing sections; only a section-final chunk may be under 300, so a sentence is split to fill a short chunk) → `ingest.py` (e5 `passage:` embeddings; topic = argmax cosine against `query:`-embedded syllabus topics, blended 50/50 with the section mean; `topic:` in `sources.yaml` pins a section after spot checks). Row IDs are uuid5 of content, so re-runs update in place; `persist` prunes sources/chunks not in the catalog but only within the ingested goal (it rejects a database holding any other goal) and never chunks cited by lessons or questions. It deletes pre-generated lessons that cite pruned chunks. Tests use `FakeEmbedder` and `tests/pdf_builder.py` instead of the model and real PDFs.
- **Embeddings** (`app/core/embeddings.py`): `Embedder` protocol shared with milestone 2 retrieval. `E5Embedder` loads sentence-transformers lazily and refuses passages longer than 512 tokens rather than silently truncating.
- **LLM** (`app/llm/`): `client.py:LLMClient` is a sync OpenAI-compatible chat-completions client (httpx) used from core code; async adapters should call it via `asyncio.to_thread`. It retries 408/409/425/429/5xx and transport errors with exponential backoff, honouring `Retry-After`. Responses are cached in `llm_cache`, keyed by a SHA-256 of URL, model and the full request body, and only the response content is stored. A cached response is served even when `LLM_ENABLED=false`; a cache miss then raises `LLMUnavailable`. `LLM_TEMPERATURE` and `LLM_REASONING_EFFORT` are sent only when set, because OpenAI reasoning models reject a custom temperature. All prompt text lives in `prompts.py`.
- **QA** (`app/core/qa.py`, `retrieval.py`): `retrieve` returns the top 8 chunks for the learner's goal, using pgvector `<=>` on Postgres and an exact Python dot product on SQLite. `QAService.ask` applies the threshold gate. It NFC-normalizes the question and redacts the learner's stored identifiers (any length, whole words, case-insensitive, also NFC-normalized) from it, plus anything shaped like a phone number, numeric channel ID (any run of 7+ digits, joined by any separators, even touching letters) or email (`privacy.redact_learner`). Raw phone numbers exist only as hashes, so they can't be matched verbatim. `qa_log` and circle-feed questions are stored with contact details redacted. The claim-check verdict must be exactly `yes` or `no`; a qualified reply falls back as `claim_check_error`. Non-text provider content raises `LLMError`. The model cites chunks by labels `C1`–`C8`, which are mapped back to IDs. The claim check sees only the cited chunks. Each `FallbackReason` and the accepted citations are logged to `qa_log` (`top_score`, `cited_chunk_ids`). `show_source` and `ask_circle` handle the `qa:src:<chunk_id>` and `qa:ask:<qa_log_id>` button payloads. `ask_circle` writes one `question` feed event per QA log, using a uuid5 ID so repeated taps can't post twice. `app.state.qa` is wired in the lifespan with a `LazyEmbedder`, so startup doesn't load torch. `UUID_LIST` is a TypeDecorator that round-trips real UUIDs on SQLite as well as Postgres.
- **Conversation** (`app/core/conversation.py`): channel-agnostic entry point. An adapter builds an `Inbound` (raw user ID, chat ID, text or button payload), and `Conversation.handle` hashes the ID on arrival, runs the whole message in one transaction and returns `Reply` objects (`app/core/replies.py`) for the adapter to send. Onboarded learners' commands are `/lesson`, `/ask`, `/progress`, `/pack`, `/language`, `/share_scores`, `/delete_me` and `/help`, and any other text goes to QA. Button payloads are namespaced: `ob:` onboarding, `acct:` account, `qa:` QA, `ls:` lessons (`ls:today` sends today's lesson, as `/lesson`), `nd:` nudges. Telegram and the web simulator both go through it; it never gives a simulated learner a chat ID.
- **Lessons** (`app/core/lessons.py`, `grading.py`): `LessonService.todays_lesson` locks the circle row and returns the circle's lesson for the current virtual UTC day (`clock.virtual_day`), creating day N+1 on the first request. The topic is `order_index` N, wrapping after the last. Generation retrieves the topic's top 6 chunks (`retrieve(..., topic_id=)`) and validates strictly: lesson ≤150 words, two questions each with options exactly A–D and an easier follow-up, citations ⊆ shown chunks for every item, then a separate claim check per item (lesson+example, each question, each follow-up) against only that item's citations. The check also verifies the marked answers. It retries once with the rejection reason appended (a different request, so the cache can't replay the bad reply), then falls back to `pregenerated_lessons`, recording `lessons.fallback_reason`. Translations (`body[lang]`, `questions.translations[lang]`) go to the model as a flat JSON object of named parts (`lessons.flatten`) and must come back with the same keys. Unchanged non-option text is rejected in code. A fidelity check (`TRANSLATION_CHECK_SYSTEM`) sees the target language and English beside the translation, and its JSON problem list feeds the retry. A failure shows English with a note. Make every LLM call before the first write in a request, because the LLM cache writes in its own transaction and SQLite would block. Grading: one answer per question (`one_answer_per_question`, insert with ON CONFLICT plus RETURNING, because psycopg reports rowcount -1), check-in and streak, private explanation + source + follow-up after a wrong answer, and one `answered` feed event per learner and lesson with no score in the payload. `grading.record_answer` is channel-free (personas use it), and `LessonService.post` translates into real members' languages only and renders the lesson for each real member.
- **Outbox** (`app/core/outbox.py`): messages a learner did not ask for (the daily lesson post and the circle update) are queued in `outbound_deliveries` with `outbox.enqueue`, in the same transaction as the work. Each row is one ordered batch of `Reply`s under a unique `deduplication_key`, and simulated learners are never queued unless a web pane controls them. `deliver_pending` (an APScheduler job every 2 s) sends batches through `AdapterRegistry` for channels with a registered adapter. Before each message it re-reads the row and learner (so a deletion during delivery cancels the rest) and renders `ScoreLine` substitutions from the owner's current `share_scores`. It retries up to `MAX_ATTEMPTS`, then sets `failed_at`, holds back that learner's later batches so nothing arrives out of order, and logs only the error type. A row with `expires_at` is never sent once the virtual clock reaches it (checked on load and again before each message), and it holds nothing back. Replies to a learner's own message still go straight back through the adapter.
- **Feed** (`app/core/feed.py`): `queue_digests` builds one "Circle update" per real member per virtual day, keyed `feed:<circle>:<learner>:<day>`, so the database enforces the batching. It shows other members' first names with check-in status. Scores come from `answers`, and only for `share_scores` members. Score lines are queued private, with a `ScoreLine` applied at send time only if the owner still opts in. It then adds `question`/`reply`/`member_left` events after the member's `(feed_delivered_at, feed_cursor_id)` cursor, never relaying a member's own events. Updates stay under `FEED_MAX_CHARS`, and events that don't fit wait for the next day's update. On the day a member is first detected as quiet, every other member's update carries a nudge prompt and button after the status lines. The nudges themselves bypass this batch.
- **Nudges** (`app/core/nudges.py`): a member is quiet when `today − (last check-in day, or join day) > QUIET_DAYS` (2), so a Tuesday check-in is detected in Friday's morning run, matching spec section 16's day-3 detection. `detect` records one `missed` feed event per quiet spell, with a uuid5 ID of circle, member and last check-in day inserted ON CONFLICT DO NOTHING, and returns only the newly detected members for that day's prompts. The `nd:s:<missed event id>` button locks the quiet member's `circle_members` row, re-checks quiet, and inserts into `nudges` ON CONFLICT on `one_nudge_per_recipient_day`. Only the winner queues the message (outbox key `nudge:<id>`, expiring at the end of its virtual day, so delivery too is limited to one per recipient per day), attributed to the tapper, with `ls:today` and `nd:later` buttons. Ajo never messages a quiet member on its own, and personas never send nudges. A persona nudged on day N checks in on day N+1 (`personas.checks_in`).
- **Simulation** (`app/sim/`): `engine.DemoEngine.run_day` is the only daily job, shared by the scheduler and `/simulate_day`. In order, it prepares today's lesson via `LessonService.post` (all LLM calls, before any write), claims `daily_runs(circle_id, virtual_day)` with ON CONFLICT (rolling back if already claimed), queues lesson posts, runs persona actions, runs the inactivity check (`nudges.detect`), and queues circle updates with the nudge prompts. Admin commands (`/seed_demo [seed]`, `/simulate_day`, `/simulate_week`, `/reset_demo` with an `adm:` confirm button, `/demo_status`) are routed by `Conversation` before its own transaction. Only raw Telegram user IDs in `ADMIN_IDS` may use them. `personas.py` defines Chidi (en, 0.9, replies to half of circle questions with a canned i18n string plus the best citation above `RETRIEVAL_MIN_SCORE`), Halima (pcm, 0.5) and Tunde (yo, 0.7, lesson days 1–2 plus the day after a `Nudge`). Every decision uses `rng(seed, persona, ...)` keyed by the item, so a seeded run repeats exactly. Personas are `Channel.WEB` learners with namespaced hashes (`personas.persona_user_id`) and no chat ID, and they answer through `grading.record_answer`. While `learners.controlled_at` is set (a web pane took control; check constraint `controlled_persona_only`), `_personas_act` skips the persona and `Learner.receives_messages` (a hybrid, usable in SQL) makes it a recipient of lesson posts, circle updates, nudges and payouts like a real member. Use `receives_messages`, never `is_simulated`, to pick message recipients. `/reset_demo` deletes the circle's lessons, feed, nudges, daily runs, weekly payouts, simulation row, personas and members' outbox rows, and calls `Clock.reset`. It keeps learners, `qa_log`, the corpus, pre-generated lessons and the LLM cache.
- **Payouts** (`app/core/payouts.py`, `pack.py`, `opportunities.py`): step 7 of `DemoEngine.run_day`, on every seventh processed day (the `daily_runs` count). It claims `weekly_payouts(circle_id, week_index)` with ON CONFLICT and queues one batch per real member, keyed `payout:<circle>:<week>:<learner>`. The batch holds private progress, a counts-only circle summary (no names, no scores, even for `share_scores` members), one opportunity, and the pack as a `Reply.file` `Attachment`. A week is the lessons posted after the previous week's end (its payout's `period_end`, or its seventh `daily_runs` row if it was never paid out), up to and including this run; answers count towards their lesson's week. `/progress` and `/pack` show the running week, or the week just paid out until the next week's first lesson. `/simulate_week` runs days until a payout, seven at most. The pack is UTF-8 text built from stored translations only (no LLM), strictly under `PACK_MAX_BYTES` (500,000); it drops lessons from the end to fit. `data/opportunities.json` is hand-checked and synced into `opportunities` at startup, and a malformed file stops startup. Each entry has a `kind` and an explicit `priority`. Selection hides passed deadlines (virtual clock) and checks older than 90 days, then orders by priority, then nearest deadline; a scholarship is ranked first, and the rehearsal checks the payout offers it. Never add unverified entries. The outbox stores attachments base64-encoded and sends them with `send_file` after the text, re-reading the learner first so a deletion stops the file; the deletion scan checks only an attachment's filename.
- **Scheduler** (`app/scheduler.py`): an APScheduler `AsyncIOScheduler` with the `deliver` job, plus a `daily` job when `SCHEDULER_ENABLED`. `DailyTicker` runs `DemoEngine.run_scheduled` (circles with a real member) when today's virtual `LESSON_TIME` falls in (previous tick, current tick]. That means no catch-up after downtime or a clock reset, and a retry on the next tick if a circle failed. Job work runs in shielded tasks that shutdown waits for.
- **Onboarding** (`app/core/onboarding.py`, `circles.py`, `account.py`): nothing is stored before "I agree". Progress then lives in the `onboarding` table, keyed by the salted channel hash, and the row is locked `FOR UPDATE` per message. The `Learner` row (difficulty 2, `share_scores` false, `consented_at`) is created only at the goal step, and the progress row is deleted in the same transaction. Goals offered are whatever the corpus ingestion created. `circles.demo_circle` gives each goal one circle with a uuid5 ID, inserted with ON CONFLICT DO NOTHING. `/delete_me` asks for confirmation, then calls `delete_learner` and adds an anonymous `member_left` feed event (no actor, empty payload).
- **i18n** (`app/core/i18n.py`): every key has `en`, `yo` and `pcm` text, with matching placeholders and untranslated `/commands` (enforced by tests). Only languages in `REVIEWED` are displayed. Others fall back to English until a native speaker signs off the review sheet, and the bot tells learners this when they pick such a language. QA answers still use the learner's language. Never generate UI strings at runtime.
- **Telegram** (`app/adapters/telegram_bot.py`): python-telegram-bot long polling, private chats only (group updates are dropped). Updates are handled one at a time, and `Conversation.handle` runs in `asyncio.to_thread`. Each `Reply` becomes a message with one inline button per row. The error handler logs the exception without the update and sends `error.generic`. `TelegramAdapter` implements `send_text/voice/file` for `AdapterRegistry`.
- **Web simulator** (`app/adapters/web.py`, `web/simulator.html`): off unless `WEB_ENABLED`; every `/web/*` request needs `Authorization: Bearer <WEB_TOKEN>` (`GET /sim`, the static page, does not). `POST /web/message` (`learner_id`, or `guest` = 32 hex for a learner still onboarding; `text` or `payload`) runs `Conversation.handle` and returns the replies directly. Unrequested messages go through the outbox to `WebAdapter`, which stores them in `web_messages` (serial ID = poll cursor, FK cascade); `GET /web/poll?learner_id=&since=` returns them. A guest's channel user ID is `sim:<guest>`, also stored as its chat ID so the learner can be picked again by ID. Panes may drive only `Channel.WEB` learners, and a persona only after `POST /web/control` (409 otherwise). `POST /web/admin` runs `DemoEngine.command`/`button` for the console as a non-learner. Startup without the simulator calls `personas.release_all`. `/reset_demo` also clears members' `web_messages`. Nothing is stored before consent: pane messages and direct replies are not kept.
- **Voice** (`app/core/voice.py`, `app/speech/`): an adapter puts a `VoiceNote(duration_seconds, fetch, size_bytes)` on `Inbound`; `fetch` is called only for an onboarded learner (no audio before consent) and within `STT_MAX_SECONDS`/size limits. `Conversation.handle` transcribes and handles `ls:listen:<lesson_id>` taps *before* opening its transaction (both take seconds; the speech cache writes in its own transaction). A transcript always goes to QA, never to command parsing, and is echoed (`voice.heard`). `stt.py`: `LocalWhisper` (faster-whisper, lazy, int8 CPU; needs PyAV < 16) or `GroqWhisper` (httpx, retries like the LLM client, fixed filename/prompt, no learner details); language hint en/pcm → `en`, yo → auto-detect. `tts.py`: `speakable` normalizes per voice (NFC keeps Yoruba tone marks; en/pcm spell numbers out and drop accents), `MMSSynthesizer` (lazy per language, seeded, one at a time), `OpusEncoder` (ffmpeg CLI; checks libopus at startup), `Speaker` caches OGG in `speech_cache` by hash of model, language, text and format. Listen plays the learner's language only if it is in `tts.AUDIO_REVIEWED` (a human sign-off, like i18n `REVIEWED`), has a model and the lesson has that translation; otherwise English with `listen.english_only`. `Reply.voice` is sent after text; voice replies are never queued (`outbox.enqueue` raises). The Listen button appears only when `LessonService(audio=True)` (TTS on).
- **Config** (`app/config.py`): pydantic-settings reads `.env`. Each integration (`TELEGRAM_ENABLED`, `LLM_ENABLED`, `STT_ENABLED`, `TTS_ENABLED`) validates its own credentials only when enabled. `SCHEDULER_ENABLED` (default false), `LESSON_TIME` (HH:MM UTC) and `DEMO_GOAL` drive milestone 5. `WEB_ENABLED` requires a `WEB_TOKEN` of 16+ characters. Tests build `Settings(_env_file=None, hash_salt=...)` explicitly instead of relying on `.env`.

## Rules from spec/plan that constrain new code

- Citation enforcement: accept an LLM answer only if the JSON matches the schema, `answerable` is true, citations are non-empty and all appear in the retrieved set, and a second claim-support check passes. Otherwise use the fallback. Log every outcome to `qa_log`.
- LLM requests must not contain learner names, IDs, chat IDs, or phone numbers; refer to a learner only by language and level. `llm_cache` is keyed by prompt hash and must never store raw prompts.
- The circle feed shows first names and check-in status only. Scores appear only when `share_scores` is true. Send at most one batched feed message per learner per day, while nudges are delivered immediately. Allow one nudge per recipient per virtual day; this is enforced by the `one_nudge_per_recipient_day` unique constraint.
- Simulation must be deterministic given a seed. Simulated personas have no `channel_chat_id` (DB check constraint). Draw persona randomness only from `personas.rng(seed, ...)` keyed by the decision, never from shared or global state.
- Queue unrequested messages through `outbox.enqueue` with a deduplication key; never call adapters from core code. Any new daily step goes inside `DemoEngine.run_day`, after the LLM-dependent lesson step.
- Use synthetic learner data only. Fixed UI strings go in `app/core/i18n.py` and are never generated at runtime.
- Tests go in `tests/test_<feature>.py` and use synthetic data and mocked external providers.
